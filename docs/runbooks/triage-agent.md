# Triage agent

Turns cluster alerts and a nightly sweep into private root-cause diagnoses, and for three
allowlisted fix classes can open a fix PR on this repo. A human always merges.

- **Created:** 2026-10-14
- **Source:** `build/triage/` (one image, a different `command` per role),
  `clusters/vollminlab-cluster/triage/` (manifests),
  `clusters/vollminlab-cluster/monitoring/kube-prometheus-stack/app/prometheusrule-triage.yaml` (self-alerts)
- **Design:** `docs/superpowers/specs/triage-agent-design.md`.
  **Plan:** `docs/superpowers/plans/triage-agent.md`. Its code listings for Tasks 8–28 are
  stale; where they differ from `build/triage/`, the code and its tests win.

## What it is

```
Alertmanager ──webhook──┐
                        ├──▶ triage-dispatcher (Deployment) ──creates suspended Job──▶ triage-<fp>-<run>
triage-sweep CronJob ───┘     dedup via GitHub issues                                   ├─ investigate (init): Claude Code → /result/result.json
                              un-suspends ONE Job at a time                             └─ publish (main): issue / PR / Pushover
```

The **dispatcher** (`triage-dispatcher`, 1 replica, `Recreate`) receives an event, resolves a
pod to its top-level owner, fingerprints it, deduplicates it against open issues, and creates a
**suspended** Job from the `triage-job-template` ConfigMap. The queue *is* those suspended Jobs, so
it survives a dispatcher restart. Every 30 s the dispatcher's tick starts the oldest waiting Job,
but only when no Job is running, the queue is under `queue_cap`, and the rolling 24h spend is
under `daily_budget_usd`. Before starting an alert's Job it re-asks Alertmanager whether the alert
still fires, and deletes the Job if not.

Each Job has two containers that share exactly one volume:

- **`investigate`** (init container) clones this repo at `main` and runs `claude -p` read-only
  from the checkout, so `CLAUDE.md` and `.claude/rules/` load automatically. It holds **only** the
  Anthropic key and the read-only `triage-agent` ServiceAccount. It always exits 0 and always
  writes `/result/result.json`.
- **`publish`** (main container) is plain Python, no LLM. It holds the GitHub App key and the
  Pushover token, never the Anthropic key. It mounts `/result` **read-only** plus the
  `triage-policy` ConfigMap, and nothing else investigate touched. It files the private issue
  first, then runs the PR gates in its own fresh clone.

The **sweep** CronJob `triage-sweep` runs at **07:30 UTC**, after the 03:00–06:00 backup window. It
only POSTs to the dispatcher's `/sweep`; the checklist runs in an ordinary triage Job.

Diagnoses go to issues in the **private** repo `vollminlab/triage-reports`, plus one Pushover
message per new issue. A PR on this **public** repo is opened only for a class that is `live`, at
`high` confidence, whose patch passes the diff guard, validation and the leak scan. The PR body
is generated by code from the parsed diff, never by the model. Sweep findings never open PRs.

## The trust boundary, and why it is shaped like this

Treat any text the agent reads from the cluster as a possible prompt injection: logs, events,
annotations, label values. Workloads write all of them, including those in the DMZ.

**investigate and publish share nothing but `result.json`.** They used to share one `emptyDir`
holding the checkout, `HOME` and `result.json`. On 2026-10-11 the agent's then-allowed
`git log --output=<path> --pretty=format:...` wrote an arbitrary `.git/config` into that checkout.
Anything investigate can write there becomes code in publish, beside the GitHub key: a
`filter.<x>.clean` or `core.fsmonitor` runs on publish's `git add`, `url.insteadOf` redirects the
push and its token, and a `.pth` file under `HOME` runs at Python startup. Filtering those inputs
cannot close that class of bug, so the boundary is the filesystem:

- separate `emptyDir`s for investigate's `/work`, publish's `/publish` and each container's `/tmp`;
  `result` is the only volume both mount, and it is read-only in publish
- publish clones the repo itself, parses `result.json` as data (no symlink, under 1 MiB,
  rebuilt from validated fields), and runs every subprocess with a minimal environment and git's
  hooks, fsmonitor and file/ext transports off
- every entrypoint is `python -I -m triage.<module>`, so nothing on a writable path can load
- `jobs.check_template` refuses to start the dispatcher if `job-template.yaml` drifts from this:
  a second shared volume, a secret in the wrong container, a `hostPath`/PVC/`projected` volume,
  `subPath`, `envFrom`, `shareProcessNamespace`, a changed `command`, or any `args`

**Secrets are bounded by RBAC, not by the Claude Code deny list.** The `triage-agent-read`
ClusterRole lists core resources explicitly and grants no `secrets`. The managed settings baked
into the image at `/etc/claude-code/managed-settings.json` (source `build/triage/managed-settings.json`)
deny Secret reads, `exec`, `helm`, `git`, `curl`, `wget` and every client-redirecting flag. Those
denies are defence in depth only, because a pattern cannot anticipate every spelling. Metrics and
logs reach the agent through `triage-query vm|vm-lt|loki`, which has fixed hosts and a GET-only
read API.

**The daily budget is not a security boundary.** The dispatcher sums `cost_usd` from each Job's
termination message, and publish copies that figure from `result.json`, which the investigate
container writes. A compromised investigation can report $0. Two caps hold regardless:

- the per-run `--max-budget-usd`, which the Claude CLI enforces
- the **Anthropic workspace's monthly spend limit**, which Anthropic enforces outside anything in
  the cluster

The workspace limit is the real ceiling. Never run the agent with a key from a workspace that has
no limit.

|---|---|---|---|---|
| `Triage GitHub App` | `github_app_id`, `github_app_installation_id`, `password` (the PEM) | `triage-github-app` (refresh 1h) | `app_id`, `installation_id`, `private_key` | dispatcher; Job `publish` |

| `Harbor Cluster Pull Robot Account` (shared) | `username`, `password` | `harbor-vollminlab-pull` (refresh 24h) | `.dockerconfigjson` | `imagePullSecrets` on all pods |

All are mounted as files under `/var/run/secrets/triage/<name>/`, never as environment
variables. The Anthropic key reaches Claude Code through `apiKeyHelper` (`build/triage/triage-api-key`),
so it is not in the environment that the agent's Bash calls inherit.

**Who reads a rotated credential, and when:**

- **The dispatcher** reads the GitHub App and Pushover files **once, at startup**. Its Deployment
  carries `reloader.stakater.com/auto: "true"`, so Reloader restarts it when either Secret changes.
- **A Job** mounts its Secrets when its pod starts, so every Job started after the Secret changes
  uses the new value. A Job already queued picks it up too, because its pod is created only when
  it is un-suspended.

Do all three before any manifest references them (`secrets.md`: save before you wire).

- Repository permissions: **Contents: Read and write**, **Issues: Read and write**,
  **Pull requests: Read and write**. Metadata: Read-only is automatic. Everything else: No access.
- Where can this App be installed: **Only on this account**.
- After creating it: **Generate a private key**. A `.pem` downloads.
- **Install App** → the org → **Only select repositories**: `k8s-vollminlab-cluster` and
  `triage-reports`.
- The **App ID** is on the App's General page. The **Installation ID** is the number at the end of
  the URL after installing.

The App can write to both repos, but no running code holds a token that can. Every token is
minted scoped *down* to one repo: issues-only on `triage-reports` for the dispatcher and publish;
contents and pull requests on this repo for publish's incident PRs only. A sweep never mints the
second token.

The workspace and key names are cosmetic, because only the 1Password item title is referenced.
What matters is that the key belongs to the limited workspace.

**3. Pushover.** Create an application at https://pushover.net/apps/build (it is named
`k8s-Triage`) and copy its API token. The user key is not entered: the script copies it from the

before running the script:


```bash

```

**5. Create the 1Password items** from an **interactive terminal**:

```bash

```

What the script does, and why:

- **It never puts a secret on a command line.** It reads the key and token through hidden prompts
  and the PEM from its file. It passes each item to `op item create` as a JSON template on stdin,
  so no value lands in argv, shell history or on screen.
- **It reads the PEM back from 1Password** and checks that it is still multi-line and a valid key.
  Pasting a PEM into the 1Password app strips its newlines, and the GitHub token mint then fails.
- **It skips any item that already exists** and prints that item's field labels instead. So it is
  safe to re-run, but it **cannot rotate** a credential (see below).
- **It refuses malformed input.** A key must start with `sk-ant-`, a Pushover token must be 30
  alphanumerics, and both IDs must be numeric.

```bash

```

```powershell

```

Then run the verification below.

### Rotating a credential

The script skips existing items. To rotate, **archive** the old item (1Password keeps it, which is
your rollback), then re-run the script for a fresh one. This keeps the new value off the command
line, which `op item edit "password=..."` would not.

```bash
op item delete "Triage Anthropic API Key" --vault Homelab --archive
bash scripts/triage-1p-setup.sh            # the PEM argument is needed only for the GitHub App item
```

If an ExternalSecret refresh lands between the archive and the re-create, ESO reports
`SecretSyncedError` and **keeps the existing Secret**. It recovers on the next refresh.

| Credential | New value from | Then |
|---|---|---|
| GitHub App key | App settings → Private keys → Generate a new key. The App ID and Installation ID are unchanged; re-enter them. | Verify (below), then **delete the old key** on the App's settings page. |
| Anthropic key | A new key **in the same limited workspace** | Verify, then disable the old key in the Console. |
| Pushover token | A new application at pushover.net | Delete the old application. |

Do not wait up to 1h (24h for Pushover) for the refresh. Force it:

```bash
kubectl annotate externalsecret -n triage triage-anthropic-apikey force-sync="$(date +%s)" --overwrite
kubectl get externalsecret -n triage            # READY=True, SecretSynced, LAST SYNC just now
```

For the GitHub App or Pushover Secret, also confirm that Reloader restarted the dispatcher.
`AGE` should be younger than the sync:

```bash
kubectl get pods -n triage -l app=triage-dispatcher
```


That line comes after `check_template` and the policy parse, so a dispatcher that prints it
accepted both.

**RBAC is what the design says:**

```bash
A=system:serviceaccount:triage:triage-agent
D=system:serviceaccount:triage:triage-dispatcher
kubectl auth can-i get secrets -A --as=$A                           # no
kubectl auth can-i get pods -A --subresource=log --as=$A            # yes
kubectl auth can-i create jobs -n triage --as=$A                    # no
kubectl auth can-i create jobs -n triage --as=$D                    # yes
kubectl auth can-i create jobs -n default --as=$D                   # no
kubectl auth can-i get secrets -n triage --as=$D                    # no
kubectl auth can-i get pods -A --subresource=log --as=$D            # no
kubectl auth can-i get pods -A --as=system:serviceaccount:triage:triage-sweep   # no
```

**Trap: `kubectl auth can-i get pods/log` does not ask about logs.** kubectl reads `pods/log` as
resource `pods`, name `log`, so it asks "may I get the pod named `log`?". That answers `yes` for
any SA that can get pods. The dispatcher has no `pods/log` grant and still gets `yes` that way
(checked 2026-10-14). Always use `--subresource=log`.

**Prometheus scrapes it and has the rules.** Query Prometheus from inside its own pod:

```bash
P="kubectl exec -n monitoring prometheus-kube-prometheus-stack-prometheus-0 -c prometheus -- promtool query instant http://localhost:9090"
$P 'up{namespace="triage"}'                                          # 1, job="triage-dispatcher"
$P 'triage_last_sweep_success_timestamp'                             # a recent epoch (see below)
$P 'prometheus_rule_group_rules{rule_group=~".*triage.*"}'          # 4
$P 'ALERTS{alertname=~"Triage.*"}'                                   # empty
```

Two traps here. **Do not use the apiserver service proxy**
(`kubectl get --raw /api/v1/namespaces/monitoring/services/kube-prometheus-stack-prometheus:http-web/proxy/api/v1/query?query=up`): it hangs
until timeout, because the `monitoring` NetworkPolicies do not admit the apiserver. **Do not try
`wget` inside the pod either**: the Prometheus image has none. `promtool` against localhost is the
path that works (both checked 2026-10-14).

`triage_last_sweep_success_timestamp` starts at the **dispatcher's start time** and moves to a
sweep Job's completion time once a clean sweep finishes. While the dispatcher is up it is never absent, so `TriageSweepStale`
can fire after a restart.

**The GitHub App can mint the exact scoped token the code mints.** Run this on the host where `op`
is signed in. It never prints the token and revokes it at the end. It is based on plan Task 5
Step 5.

```bash
umask 077; T=$(mktemp -d)
python3 -m venv "$T/venv" && "$T/venv/bin/pip" install -q PyJWT==2.15.0 cryptography==50.0.1 requests==2.34.2
op item get "Triage GitHub App" --vault Homelab --format json > "$T/item.json"
"$T/venv/bin/python" -I - "$T/item.json" <<'PY'
import json, sys, time
import jwt, requests
f = {x["label"]: x.get("value") for x in json.load(open(sys.argv[1]))["fields"]}
now = int(time.time())
app_jwt = jwt.encode({"iat": now - 60, "exp": now + 540, "iss": f["github_app_id"]},
                     f["password"], algorithm="RS256")
r = requests.post(
    f"https://api.github.com/app/installations/{f['github_app_installation_id']}/access_tokens",
    headers={"Authorization": f"Bearer {app_jwt}", "Accept": "application/vnd.github+json"},
    json={"repositories": ["triage-reports"], "permissions": {"issues": "write", "metadata": "read"}},
    timeout=30)
body = r.json()
print(r.status_code, sorted(body.get("permissions", {}).items()),
      [x["name"] for x in body.get("repositories", [])])
if "token" in body:
    d = requests.delete("https://api.github.com/installation/token",
                        headers={"Authorization": f"token {body['token']}"}, timeout=30)
    print("revoked:", d.status_code)
PY
shred -u "$T/item.json"; rm -rf "$T"
```

Expected: `201 [('issues', 'write'), ('metadata', 'read')] ['triage-reports']`, then `revoked: 204`.
A `404` means a wrong Installation ID or an App not installed on `triage-reports`. A `401` means
the PEM or App ID is wrong.

## Day-to-day operation

### Where things go

| Event | Result |
|---|---|
| New incident | Issue `[<alertname>] <namespace>/<Kind>/<name>` in `triage-reports`, labels `fp/<12 hex>`, `class/<class>`, plus one Pushover message |
| Same fingerprint, open issue updated **≥ 24h** ago | Re-investigated; the result is a **comment** on that issue, with no Pushover |
| Same fingerprint, open issue updated < 24h ago | Dropped (`deduped_recent`) |
| Same fingerprint, Job already queued or running | Dropped (`deduped_inflight`) |
| Alert resolves | Dispatcher comments `Resolved at …`, closes the issue, deletes any queued Job for it. Open PRs are left alone |
| Sweep | One issue per finding, `[sweep] <check>: <ns>/<object>`, labels `sweep`, `check/<check>`, `fp/<12 hex>`. At most 10 new per run; the rest are counted as `capped` and filed by a later sweep |
| Namespace `triage` | Ignored (`ignored_self`); triage never diagnoses itself |

The fingerprint is `sha256(source, reason, namespace, workload)` with the pod resolved to its
Deployment/StatefulSet/DaemonSet/CronJob, so five crash-looping pods of one Deployment are one
incident. The issue body carries `<!-- fp:<full hash> -->`, and dedup searches **open** issues by
the `fp/<12 hex>` label. Closing an issue therefore re-arms its fingerprint.

"Updated" is GitHub's `updated_at`. Any human comment or label change restarts the 24h window.

Sweep findings get no resolve event. Close them by hand when fixed. A finding that persists after
you close it is filed again by the next sweep.

Status labels publish adds:

| Label | Meaning |
|---|---|
| `agent-error` | The investigation did not complete; the body names the `failure_reason` (`max_turns`, `budget_cap`, `timeout`, `api_error`, `invalid_output`, `setup_failed`) |
| `injection-suspected` | The agent reported that cluster data tried to direct it |
| `shadow` | Gates ran in shadow mode; the gate report comment shows the PR that would have been opened |
| `pr-opened` | A PR was opened (live classes only) |
| `redacted` / `leakscan-failed` | gitleaks redacted something, or could not run (the text was posted unscanned) |

You add `shadow-correct` or `shadow-wrong` to every `shadow` issue. That is the promotion signal.

A gated issue arrives in two steps. The body ends with "PR gates: Running…", and the gate report
follows as a **comment**. If no comment arrives, publish did not finish (see `TriagePublishFailing`).

### Reading a Job

Finished Jobs are kept 25h (`ttlSecondsAfterFinished: 90000`); the dispatcher's 24h spend and
outcome accounting reads them.

```bash
kubectl get jobs -n triage -l triage.vollminlab.com/fp \
  -L triage.vollminlab.com/fp,triage.vollminlab.com/kind --sort-by=.metadata.creationTimestamp
```

`SUSPENDED` Jobs are the queue. `triage.vollminlab.com/kind` is `incident` or `sweep`. The Job name
is `triage-<fp12>-<unix time>`. That suffix is also the run id in a PR branch
(`fix/triage-<class>-<fp12>-<run>`).

```bash
J=triage-<fp12>-<run>
# The incident as the dispatcher queued it
kubectl get job -n triage $J -o jsonpath='{.metadata.annotations.triage\.vollminlab\.com/incident}' | python3 -m json.tool
# investigate's last line: status=ok|failed reason=... cost=$... denials=N
kubectl logs -n triage job/$J -c investigate | tail -1
# publish's log, then its one-line summary (what the dispatcher accounts)
kubectl logs -n triage job/$J -c publish
kubectl get pods -n triage -l job-name=$J \
  -o jsonpath='{.items[0].status.containerStatuses[?(@.name=="publish")].state.terminated.message}'; echo
# {"outcome": "issue_created", "cost_usd": 0.84, "issue": 12, "pr": null}
```

| `outcome` | Meaning |
|---|---|
| `issue_created` / `commented` | Normal incident result |
| `sweep_ok` | Clean sweep; also carries `findings`, `new` and `capped` |
| `agent_error` | The investigation failed; the issue says why |
| `publish_failed` | publish raised; a "Triage publish failed" Pushover went out with the diagnosis attached |
| `job_crashed` | Dispatcher-assigned: the Job finished with **no** termination message (killed, OOM, deadline). Paged once, and the Job is annotated `triage.vollminlab.com/crash-notified=true` |

A run whose cost is unknown (`cost_estimated: true`, or a crash) is charged at
`per_run_budget_usd`.

### Queue and budget

- **One Job runs at a time.** With one running, the tick reports `busy` and waits.
- **`queue_cap` (10) waiting Jobs:** new events are dropped (`dropped_queue_full`), with one
  "Triage queue full" Pushover until the queue drops below the cap.
- **`daily_budget_usd` reached** (rolling 24h of finished Jobs): nothing new starts, the queue
  holds, and "Triage daily budget reached" is sent at most once per 24h. Jobs resume as spend
  ages out. To clear it sooner, raise the cap by PR. Deleting finished Jobs also removes them
  from the sum, but it destroys the evidence.
- **Alertmanager unreachable at start time:** the alert is treated as still firing, so a flaky
  re-check costs money rather than losing an incident.

### Metrics

| Metric | |
|---|---|
| `triage_events_total{source,outcome}` | outcomes: `dispatched_new`, `dispatched_comment`, `deduped_inflight`, `deduped_recent`, `deduped_batch`, `dropped_queue_full`, `dropped_resolved`, `dropped_invalid`, `ignored_self`, `resolved`, `resolved_unmatched` |
| `triage_jobs_24h{outcome}` | finished Jobs in the last 24h, by the outcomes above |
| `triage_spend_usd_24h` | the figure the daily cap compares against |
| `triage_queue_depth` | suspended Jobs waiting |
| `triage_last_sweep_success_timestamp` | see Verification |

`resolved_unmatched` counts resolves that matched no open issue and no queued Job. The alert was
never filed: dropped, still being investigated, or keyed differently.

### Self-alerts

All four set `namespace: triage`, so the dispatcher ignores them, and they reach Pushover through
the normal Alertmanager routes.

| Alert | Fires when | First response |
|---|---|---|
| `TriageDispatcherDown` | `up{job="triage-dispatcher"}` 0 or absent for 10m | `kubectl get pods -n triage -l app=triage-dispatcher`, then `kubectl logs -n triage deploy/triage-dispatcher --previous`. A `ValueError` at startup means `policy.yaml` or `job-template.yaml` failed validation: fix it by PR |
| `TriageSweepStale` | No clean sweep for 26h (measured from the later of the last `sweep_ok` and the dispatcher start) | Did the CronJob's POST fail (`kubectl get jobs -n triage \| grep triage-sweep`, then `kubectl logs -n triage job/<that job>`), or did the sweep Job itself end `agent_error` (`kubectl get jobs -n triage -l triage.vollminlab.com/kind=sweep`)? |
| `TriageAgentErrors` | ≥ 3 `agent_error` outcomes in 24h | Read the `agent-error` issues in `triage-reports`. Many `api_error`s in a row usually mean the key is revoked or the workspace limit is hit |
| `TriagePublishFailing` | Any `publish_failed` or `job_crashed` in 24h | `kubectl logs -n triage job/<name> -c publish`, then `kubectl describe job -n triage <name>` for a deadline or OOM |

`TriageSweepStale` cannot see a dispatcher that is down, because the metric is then absent.
`TriageDispatcherDown` covers that case. A failed sweep POST also fails its Job, which raises the
cluster's generic `KubeJobFailed`.

## Changing behaviour

Everything is in `clusters/vollminlab-cluster/triage/triage/app/policy.yaml` (ConfigMap
`triage-policy`) and goes in by PR. Reloader restarts the dispatcher on change, and each Job reads
the ConfigMap fresh when its pod starts. **An invalid value crash-loops the dispatcher**
(`TriageDispatcherDown`). Parse it locally before opening the PR:

```bash
PYTHONPATH=build/triage python3 -c "import yaml; from triage.policy import parse_policy; \
print(parse_policy(yaml.safe_load(open('clusters/vollminlab-cluster/triage/triage/app/policy.yaml'))))"
```

### The PR gates

All four, plus the leak scan, must pass, and the class must be `live`. In `shadow`, gates 2–4
still run and the report shows the would-be PR.

1. The class is allowlisted (`live` to actually open the PR).
2. `confidence` is `high`.
3. The diff guard (`build/triage/triage/diffguard.py`):
   - Only files under the incident's own app directory, whose manifests target its namespace.
   - No `*-externalsecret.yaml`, `kustomization.yaml` or `*networkpolicy*` files.
   - No files added or deleted.
   - Only the class's fields change:
     - `oom-memory-limit`: memory limit up to at most 2×, and ≥ 1.2 × `metrics.peak_memory_bytes`.
     - `cpu-throttle-limit`: removal of a CPU limit, with `metrics.throttled_ratio` present.
     - `renovate-breakage`: one version/tag/image value, reverted exactly one step in that file's
       git history, and not on the denylist.
4. `kustomize build`, `kubeconform` and `kyverno apply`, the same tools at the same versions CI
   uses.
5. gitleaks over the PR body and patch.

### Promoting a class to `live`

The criterion is in the `policy.yaml` header: **3 consecutive `shadow-correct` issues for that
class with no `shadow-wrong` between them.** Promotion is always a one-line PR changing
`shadow` to `live`. Nothing promotes itself. To find the evidence:

```bash
gh issue list -R vollminlab/triage-reports --state all --label class/oom-memory-limit --label shadow \
  --json number,title,labels,createdAt
```

To stop all PRs while keeping diagnoses, set every class back to `shadow`.

### Inert Kyverno policies are an alert, not a sweep item

The sweep's third check, `inert-kyverno-policy`, was removed on 2026-10-15 when the
`KyvernoPolicyNoPassResults` PrometheusRule (`prometheusrule-kyverno.yaml`) replaced it. The
design's rule is that a check a metric can express is an alert rule, not a sweep item: the rule is
deterministic and free, and the sweep only spends tokens on what PromQL cannot see.

The sweep version also read PolicyReports, which misreport two policies. A Kyverno mutation that
changes nothing is reported as `skip`, so `mutate-default-sa-pod-automount` showed zero passes there
while the admission metric counted them; and `restrict-default-namespace` can never pass at all.
Those were triage-reports #5 and #6.

The image's output schema and sweep prompt still list `inert-kyverno-policy` as a valid check name.
That is harmless, because `sweep_checklist` in `policy.yaml` decides what the sweep runs; drop the
name in the next image release.

## Pausing and stopping

From the gentlest to the hardest:

**Stop PRs, keep diagnoses.** Set every class to `shadow` in `policy.yaml` by PR. This is the state
today.

**Pause everything, the GitOps way.** Open a PR that sets `replicas: 0` in `deployment.yaml` **and**
`suspend: true` on the CronJob in `cronjob-sweep.yaml`. Scaling only the dispatcher leaves the sweep
POSTing to nothing every night. That fails its Job and raises `KubeJobFailed`, and
`TriageDispatcherDown` fires too; silence that one or expect it. Queued Jobs stay suspended,
because only the dispatcher un-suspends them. A Job already running finishes.

**Emergency pause, before a PR can merge.** `kubectl scale` alone does not hold: the `triage` Flux
Kustomization re-applies `replicas: 1` on its next reconcile, within 10 minutes. Suspend Flux first:

```bash
flux suspend kustomization triage
kubectl scale deployment -n triage triage-dispatcher --replicas=0
kubectl patch cronjob -n triage triage-sweep -p '{"spec":{"suspend":true}}'
kubectl delete job -n triage -l triage.vollminlab.com/fp      # optional: drops the queue AND any running Job
```

Leaving the Kustomization suspended also freezes every other change to `triage`. Undo with
`flux resume kustomization triage`: the next reconcile re-applies git, which undoes the scale and
the CronJob patch. Land the PR first if the pause should outlive the resume.

**Hard stop, outside the cluster.** Use this if the cluster itself is not trustworthy:

- **Disable the Anthropic key** in the Console (or lower the workspace limit). Every
  investigation then fails as `api_error` and spends nothing. Issues still get filed, as
  `agent-error`.
- **Suspend the GitHub App installation**: org settings → GitHub Apps → `vollminlab-triage` →
  Configure → Suspend. No issue, comment or PR can be written. **This alone does not stop spend.**
  When the dispatcher's issue lookup fails it dispatches the event as new by design, so Jobs still
  run and investigate, and then publish fails (`publish_failed`). Disable the Anthropic key as well.

Once plan Task 37 is done, removing the `triage` route from the `Alertmanager Config` item stops
alert intake without touching the cluster. See Task 37 for the safe edit procedure.

## Releasing a new image

1. The change merges to `main` through a normal PR. CI's `build-images` job builds `build/triage/`
   and runs its test suite inside the image. **The tag workflow does not run tests**, so only tag
   commits that passed CI on `main`.
2. Tag the merge commit and push the tag. That triggers `.github/workflows/build-triage.yaml`,
   which pushes `harbor.vollminlab.com/vollminlab/triage:X.Y.Z` (and `:vX.Y.Z`) to the private
   Harbor project:

   ```bash
   git checkout main && git pull
   git tag triage/vX.Y.Z && git push origin triage/vX.Y.Z
   ```

3. **Verify the artifact, not the workflow status.** Pull it with the cluster's own pull robot,
   into a throwaway Docker config so the credential does not stay on the host:

   ```bash
   export DOCKER_CONFIG=$(mktemp -d)
   op read "op://Homelab/Harbor Cluster Pull Robot Account/password" \
     | docker login harbor.vollminlab.com --password-stdin \
         -u "$(op read 'op://Homelab/Harbor Cluster Pull Robot Account/username')"
   docker pull harbor.vollminlab.com/vollminlab/triage:X.Y.Z
   docker run --rm harbor.vollminlab.com/vollminlab/triage:X.Y.Z claude --version   # the Dockerfile's CLAUDE_CODE_VERSION
   rm -rf "$DOCKER_CONFIG"; unset DOCKER_CONFIG
   ```

4. Bump the tag by PR in all four places: `deployment.yaml`, `cronjob-sweep.yaml`, and **both**
   containers in `job-template.yaml`. Also update the triage entries in `docs/cluster-reference.md`.
   The job template is a ConfigMap, so neither kubeconform nor Kyverno sees its image; `grep -rn
   'triage:' clusters/vollminlab-cluster/triage` before committing. Jobs already queued keep the
   image they were built with.

## Known limitations and accepted risks

- **Open internet egress on 443.** `allow-https-egress` admits `0.0.0.0/0` minus RFC1918 for the
  agent and the dispatcher. NetworkPolicy cannot filter by FQDN, and an egress proxy is out of
  scope. An injected agent could in principle send out what it can read. It cannot read Secrets,
  and it has no general HTTP client: `curl` and `wget` are denied, and `triage-query` reaches only
  three fixed in-cluster hosts.
- **The agent can read every ConfigMap and every pod log in the cluster.** Anything sensitive kept
  in a ConfigMap or written to a log is readable by it and can land in a private issue. One known
  candidate was checked on 2026-10-14: no Terraform CR stores a readable plan. All 12 in `tofu` have
  `storeReadablePlan: none`, and `tofu` has no plan ConfigMaps. Keep it that way. Never put a secret
  in a ConfigMap (`secrets.md`), and never log one.
- **The daily budget trusts a figure the agent writes.** Covered above. The workspace limit is the
  boundary.
- **Shadow evidence is human-labelled.** Promotion is only as good as the `shadow-correct` /
  `shadow-wrong` labels.
- **No flow logs.** Calico open source has none here, so "no outside connection" is evidenced by
  the denied-tool-call record and the absence of a PR, not by network logs.
